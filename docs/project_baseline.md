## 部署架构

```text
开发终端
  |
  +-- 本地 WSL2 / Windows 开发环境
  |
  +-- CPU 运行环境（本地或 4 vCPU / 16 GiB CPU ECS）
        |-- AIOS Agent 编排
        |-- 受控工具
        |-- Docker Linux 故障靶机
        |
        +-- HTTPS / OpenAI 兼容接口
              |
              +-- 远程 GPU vLLM
                    |-- Qwen2.5-7B AWQ 4bit
                    |-- 端口按云安全策略限制
```

## 架构决策

1. 模型仅部署在一台远程 GPU vLLM 服务上，所有 Agent 共享该服务。
2. CPU 侧承担任务编排、工具调用、状态记录和故障靶机，不加载模型。
3. 本地 RTX 4060 8 GB 用于开发验证，不作为最终性能结论的唯一环境。
4. 300 元 CPU 权益不是 W01A 的前置条件；本地环境跑通后才决定是否启用 CPU ECS。
5. 正式性能实验必须记录 Agent 与 CPU 环境、远程 GPU 环境、网络链路和模型参数。
6. 本地 Ollama 仅作为逻辑调试替身，最终提交仍以远程 vLLM 和 AWQ 4bit 为基线。

## CPU 服务器决策

W01A 阶段不需要 CPU ECS。本地 Python 环境、脚本开发和接口测试先完成。

进入 W07 最小闭环联调后，建议启用按量付费 CPU ECS，原因是本机同时运行 Windows、WSL2、AIOS、Docker 靶机和日志工具时，16 GiB 内存余量较小。CPU ECS 可以稳定承载 Agent 编排与靶机，模型仍留在远程 GPU vLLM。

首选规格：

- 实例族：经济型 e；
- 规格：4 vCPU / 16 GiB；
- 规格名：`ecs.e-c1m4.xlarge`；
- 计费：按量付费；
- 系统：Ubuntu 22.04；
- 磁盘：默认 40 GiB 起步；若允许加盘，建议 80 GiB；
- 地域：优先选择与远程 GPU 网络延迟较低、且有库存的地域；
- 安全组：SSH 和管理端口仅允许团队固定 IP。

不选择 2 vCPU / 2 GiB、2 vCPU / 4 GiB、2 vCPU / 8 GiB 实例，因为它们无法稳定同时承载 AIOS、Docker 靶机、Redis/Chroma 和测试工具。CPU ECS 不承担 7B 模型推理。

## 强制流程

`故障上报 -> 四路证据并行采集 -> 证据汇合与诊断 -> 受控修复 -> 独立验证 -> 成功归档或失败重试`

## 安全管理

- 代码与文档不得出现 AccessKey、密码、私钥或真实模型 API Key。
- 故障修复只允许作用于隔离靶机。
- 修复操作使用白名单工具和回滚点。
- 远程模型端点必须通过受限安全组或 VPN 访问。
